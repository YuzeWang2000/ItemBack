# ItemBack UI 设计原则

本文档是 ItemBack 后续 UI 设计与评审的基线。目标不是冻结界面，而是在增加能力时继续保持产品简洁、安静、美观，并让新旧功能看起来属于同一个系统。

## 产品气质

ItemBack 是面向长期持有的个人物品档案，而不是高频操作的管理后台。界面应像一份耐看的私人档案：温和、可靠、有秩序，不过度装饰，也不过度暴露系统复杂度。

现有视觉语言包括：

- 暖白纸张色背景、深森林绿主色、琥珀色小面积强调和低饱和危险色。
- 正文使用清晰的系统无衬线字体，页面与区块标题使用 Georgia 衬线字体形成档案感。
- 轻边框、克制阴影、中等圆角和留白充足的卡片布局。
- 以内容层级和间距建立秩序，避免依赖高饱和色、大面积渐变或多重装饰。
- 文案简短、自然、具体，优先使用用户理解的“物品、空间、位置、归档”等词汇。

具体色彩变量与基础控件以 `apps/web/src/styles.css` 为准，共享状态组件以 `apps/web/src/components/ui.tsx` 为准。

## 设计原则

### 1. 一个区域只有一个主要意图

页面标题区、卡片或表单区应有明确的首要任务。一个区域默认只放一个主要按钮；其他操作使用次要按钮、文字操作、上下文菜单或渐进披露。危险操作不得与主要操作争夺视觉注意力。

### 2. 让复杂度随需要出现

低频设置、高级筛选、解释性细节和次要操作不应永久占据主流程。优先使用合理默认值、分组、折叠、分步流程或上下文操作，但不能因此隐藏完成任务所需的关键信息。

### 3. 复用既有层级与组件

新页面沿用 `PageHeader`、`panel`、`Field`、`Notice`、`Loading`、`Empty`、现有按钮层级和响应式容器。只有当现有模式确实不能表达新的用户任务时，才增加新组件或视觉规则；新增模式必须可复用，而不是页面内的一次性例外。

### 4. 信息先于装饰

视觉元素必须帮助识别对象、状态、关系或下一步操作。不要为了“丰富”页面而增加无含义图标、徽章、色块、动画或重复说明。数据密集区域优先通过分组、对齐、留白和文字层级解决。

### 5. 所有状态属于设计的一部分

根据功能覆盖加载、空、错误、成功/完成、禁用、无权限或不可用等状态。反馈应出现在操作发生的上下文中，说明发生了什么以及用户下一步能做什么，避免只依赖颜色表达状态。

### 6. 响应式与可访问性不是降级项

界面从 320px 宽度起应保持无横向溢出，主要操作可触达，信息顺序合理。交互元素使用正确语义、可见焦点和明确标签；文本与背景保持足够对比度；动画不应妨碍操作。

## 新功能进入 UI 的流程

实现前先回答：

1. 用户要完成的单一核心任务是什么？
2. 该任务应进入哪个现有页面或流程，能否复用已有模式？
3. 哪些信息必须立即可见，哪些可以按需出现？
4. 新入口是否挤占更高频任务，或使一个区域出现多个同等突出的主要操作？
5. 桌面、窄屏、键盘操作及各类状态分别如何呈现？

实现时优先选择满足任务所需的最低界面复杂度。这里的“最低”不是删减必要能力，而是减少常驻控件、重复信息、视觉噪声与新概念。

## 设计冲突门槛

出现下列任一情况时，不应直接实现需求：

- 为低频或次要功能长期占用主导航、页面标题区或主要内容区域。
- 在同一区域堆叠多个同等突出的主操作，导致下一步不清晰。
- 必须另起一套色彩、字体、间距、图标或交互语言，且没有产品层面的充分理由。
- 只能在桌面宽屏成立，在窄屏下需要隐藏关键能力或造成明显拥挤。
- 依赖模糊图标、颜色或隐蔽手势，无法让用户理解操作或状态。
- 为赶进度绕开共享组件，产生一次性视觉例外或重复模式。
- 新功能明显打断“查找—查看—记录/更新物品”的主要任务流。

遇到冲突时，开发应暂停在 UI 实现之前，说明受影响的页面、冲突的原则和用户体验风险，并给出一至两个更简洁的替代方向。功能完成标准不能靠牺牲必要能力来缩小；如果替代方向仍无法同时满足功能与本规范，应要求重新设计需求后再继续。

## UI 变更验收清单

- 核心任务和主要操作一眼可辨；每个区域至多一个主要按钮。
- 使用现有设计变量、共享组件和既有文案语气；新增模式有明确复用价值。
- 页面没有重复说明、无含义装饰、常驻低频控件或不必要的新层级。
- 加载、空、错误、完成及禁用状态与正常状态同样经过设计。
- 320px 起的窄屏与桌面布局均无横向溢出、遮挡或关键操作丢失。
- 键盘焦点、语义标签、对比度和非颜色状态提示可用。
- 对改动页面进行视觉核对，在评审中提供桌面与窄屏截图，并运行相关 lint、测试和构建；涉及关键用户流时补充或更新 Playwright 验收。

若任何一项不满足，UI 变更尚不能视为完成。
